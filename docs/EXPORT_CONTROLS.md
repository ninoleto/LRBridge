# Native Export controls (v0.6)

Native button behavior was accepted by the user on 2026-09-17 after restarting LRBridge and Lightroom: **Export…** opened Lightroom's full Export dialog; **Export with Previous** opened Lightroom's destination-folder chooser; the web controller correctly displayed **one selected photo**. This does not establish completed file export, dialog cancellation or multi-photo export behavior. The agent invoked no production export during development. Custom named-export-preset discovery/import/execution is deferred.

The Selection page has a compact Export section. **Export…** requests `photo:openExportDialog()`. **Export with Previous** requests `photo:openExportWithPreviousDialog()` and explains that it reuses Lightroom's last export settings and may start immediately. Both methods are documented from SDK 7.4. Library and Develop are supported contexts; controls fail closed without fresh native selection feedback.

The SDK wording does not guarantee that Export with Previous opens a dialog. MIDI2LR implements its Export again command with this method. Treat it as an action that may write output immediately, subject to Lightroom's settings and prompts. Neither method documents a completion result or dialog-open/cancel observer. LRBridge reports **requested**, **stale**, or **uncertain**, never export completion. Successful return after cancelling a native dialog still means only that the SDK request was made.

## Selection and dispatch

- A read-only `export.query` uses the existing FIFO command queue, on demand while Export is visible. At most one query is outstanding, at most once per second. Existing command/feedback polling loops and intervals are unchanged. Leaving the section stops its reads unless an action still needs reconciliation.
- Lua retains the actual catalog object and path, active-photo local identifier and UUID, module, and the exact sorted set of every selected photo's `localIdentifier`. Adobe documents that read-only identifier as unique within its catalog. Only an opaque selection token, count and capability flags leave Lua; catalog paths and selected-photo lists are not sent to the browser.
- A missing active photo is rejected before using `getTargetPhotos()`: that API otherwise falls back to the entire Filmstrip. Duplicate/missing identifiers, a selection lacking the active photo, failed reads, unsupported methods and unstable reads fail closed. Reordering the same membership is harmless. Same-count replacement of a non-active selected photo is detected.
- Capture checks the entire native identity again after the potentially yielding UUID metadata read. Immediately before invocation, Lua consumes a one-use server claim, then repeats the catalog, active-photo UUID and full selection check. There is no HTTP call or explicit yield between the final native check and the SDK invocation. SDK-internal behavior after invocation remains controlled by Lightroom.
- Every request invokes exactly one method on the active `LrPhoto`; no loop over the selected photos and no selection rewrite. MIDI2LR's single-call wrapper documents selection-wide effects. Native observation covered one selected photo; multi-photo behavior remains untested. Complete-selection safeguards have automated coverage, not additional native acceptance.
- Server epoch, context/Develop counters, context timestamp, fresh selection token and state revision bind admission. Queue ownership rejects forged, duplicate, stale or batch-injected commands. A request ID remains consumed for the server epoch, including after an error or timeout; an identical resubmission returns a receipt without queuing another call. Reusing an ID with changed inputs is rejected. The bounded receipt store refuses new IDs at capacity rather than evicting old IDs.
- Export actions form queue coalescing boundaries: later slider/reset/gesture input cannot remove an earlier edit across a queued Export action. Without a queued Export action, existing coalescing behavior is unchanged. Export queries and actions use ordinary queue capacity, preserving the protected editing reserve.
- Lua records operation high-water marks before network/SDK work. Server claim consumption also prevents duplicate invocation after a module reload. Reload loses the native selection lease and requires a fresh query. Shutdown and generation changes reject old work. Existing polling recovery never requeues the command.
- A dispatched request that times out, loses its result, or returns ambiguously becomes uncertain. Export buttons stay disabled until the user checks Lightroom and explicitly acknowledges the uncertainty; that acknowledgement sends no export. Browser transport failures reconcile by reading state, never by repeating an action. Shared Undo/Redo stays blocked while dispatch/reconciliation is pending. Export adds no fabricated editing/history result.

## HTTP contract

All endpoints below use the existing local HTTP server and `GET` conventions. Controller proxy paths have the `/api` prefix. Responses are not cached. Exact query field sets reject extra/duplicate fields.

1. `GET /export/state` returns the authoritative snapshot, requests a bounded read if needed, and includes `serverEpoch`, `revision`, `selectionToken`, `selectionCount`, context fields, `pendingOperation`, `lastResult`, and `needsReview`. A caller must wait for `available: true` and fresh `ageMs` before submitting.
2. `GET /export/action` requires `command=export.dialog|export.previous`, a unique `requestId`, `serverEpoch`, `stateRevision` (snapshot `revision`), `selectionToken`, `activeModule`, `selectedPhotoUuid`, `contextCounter`, `developCounter`, and `contextChangedAt`, all from one snapshot. Missing/extra/duplicate fields or an unsupported command produce 400; unavailable/busy state, invalid binding values or stale bindings produce 409. Success admits the request, not the export outcome. Never retry automatically.
3. `GET /export/acknowledge` requires `serverEpoch` and the uncertain result's `operationId`. It clears the review interlock only after explicit user acknowledgement and never invokes Lightroom.

`/export/query-result`, `/export/claim`, and `/export/operation-result` are plug-in protocol endpoints bound to outstanding requests. The internal `export.query` and the two action commands cannot bypass ownership through `/command`, WebSocket or a command batch. Normal consumers use `/export/action` with a fresh snapshot.

The module uses Lightroom SDK catalog/photo/HTTP/task APIs and portable Lua. It contains no UI automation, keyboard/mouse injection, window inspection, or Windows path assumptions. No production dependency was added.

## Verification and manual acceptance

Focused coverage: real HTTP admission plus production queue/Parser/Commands/Export Lua with a mock SDK; request and query duplicates, one-use claims, selection replacement/addition/reordering, catalog object/path changes, active UUID/module changes, metadata-read races, no-photo/error paths, SDK false/throw, expiry, late responses, shutdown/generation changes, reload and uncertain-result review. Isolated browser coverage includes both labels, warning accessibility, 44px targets at 1280/768/390/320, focus retention, pending/duplicate clicks, stale revisions/epochs, lost admission, no retries, unavailable capabilities and inactive-page polling cleanup.

The user restarted both LRBridge and Lightroom before reporting and accepting the three observations above. The implementation is loaded; recording this acceptance and creating its checkpoint require no further restart, plug-in reload or controller refresh.

The destination chooser is the observed Previous behavior for that test, not a guarantee of a prompt with other last-used settings. Completed output, cancellation and multi-photo export were not reported tested, and this checkpoint makes no such claims. Native stale-selection/duplicate/error cases and comprehensive editing/polling regression were not manually established by the button test; their focused automated coverage remains separate. No further native test is required for this accepted button checkpoint. If file-output or multi-photo testing is requested later, first confirm the exact selection, destination, settings and collision behavior; only the user starts the controlled export. No push, tag or release is included.
