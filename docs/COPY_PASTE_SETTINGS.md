# Native Copy / Paste Settings (v0.6)

September 27 acceptance: the user reports Copy/Paste working in the cases tested, with no problems observed, and accepts the simplified help/result presentation. The report does not enumerate additional scenarios, photo counts or AI/mask-preservation checks; do not infer those were tested. Automated fixtures remain separate and never invoke Lightroom or the user's clipboard/photos. The accepted Export behavior and required Dust presets are preserved.

## Native behavior and limits

- **Quick Copy Settings** calls `activePhoto:copySettings()` once in an SDK task, using the categories last chosen in Lightroom's native Copy Settings dialog. It copies from the active photo even when several photos are selected. The public SDK has no opener for that native chooser and no category-selection argument. This button has no ellipsis and does not promise a dialog. The label is presentation only; its action ID remains `clipboard.copy`, including existing saved favorites.
- **Paste Settings** uses Lightroom's settings clipboard for the complete captured selection. One target uses `photo:pasteSettings(true)`; multiple targets use `catalog:pasteSettings(capturedPhotos, true)` once. There is no per-photo paste loop, source-photo exclusion, selection rewriting, raw Develop-settings reconstruction or OS clipboard integration. Settings copied directly in Lightroom work without a prior web Copy.
- The SDK uses clipboard contents at execution time. It provides no contents/categories/validity/version getter; LRBridge cannot freeze or verify what was on the clipboard at click time. Selection availability is not clipboard validity. External native Copy operations can replace the clipboard while a request is queued.
- Copy/single-photo Paste document Boolean success. Catalog Paste returning true establishes execution for **at least one photo**, not success for the entire batch. False, an exception, a non-Boolean return, lost result or post-invocation gate error is not a reason to retry. No specific empty-clipboard/cancellation diagnosis is fabricated. The API exposes no cancellation callback or cancellable operation handle.
- `updateAISettings=true` requests automatic AI updating. The default documented by the SDK is false; LRBridge deliberately passes true under the user's accepted product decision. The SDK does not specify mask merge/replace behavior or guarantee preservation of existing AI edits, completion of all processing, or visual correctness. No automatic AI-update follow-up, rollback or retry is performed.
- After Paste, read-only `needsUpdateAISettings()` calls on the captured destinations report pending AI counts when readable. These sequential reads are status at their respective read times, not an atomic batch snapshot or completion observer. Unknown status stays unknown; zero pending does not prove successful AI processing or preservation. The receipt records how many photos were checked and never adopts a newly selected destination.

Photo methods were introduced in SDK 10.3; the AI argument and catalog Paste are documented in SDK 15.3. These are portable Lightroom SDK calls, with no Windows UI automation, simulated input or new production dependency. The reference imposes an asynchronous task for Copy; Paste also requires catalog write access. Supported controller contexts are Library and Develop, with native capability checks.

## Controller and safeguards

**Copy / Paste Settings** is the final section in Selection, after Export; Navigate is first. Its two buttons are followed by three short help paragraphs explaining **Ctrl+Shift+C**, **Quick Copy Settings** and **Paste Settings**. Destination photos are selected in Lightroom; the Controller has no destination-count line or technical Details panel. Progress, results and errors appear directly below the help. Batch results state that Lightroom confirmed pasting to at least one photo, without claiming every photo was updated. AI results distinguish updates still needed, none reported as pending on the checked photos, and unknown status; users still review the photos in Lightroom. Any required **I’ve checked Lightroom** acknowledgement remains visible. Empty feedback reserves no height. Favorites use brief action-specific submission messages outside the bar; expiry never discards the section's result or required review workflow. Selection capture, validation and native Copy/Paste behavior are unchanged.

The section retains its element identities when detached/re-attached across tabs. Copy/Paste use `aria-disabled` plus guarded activation so pending/unavailable states do not drop keyboard focus; they remain focusable but cannot submit. The former global information block, reserved blank feedback space and two-row toolbar are removed. A compact [favorites bar](CONTROLLER_FAVORITES.md) defaults to Undo/Redo; users can add Copy/Paste and Export actions without separate dispatch paths. Its measured height also sets the sticky navigation offset. Existing Undo/Redo native availability, cooldown, gesture/history interlocks and focus styling remain. Paste settlement refreshes authoritative context, Develop/Masking feedback and native history; Copy creates no invented history change.

Read-only `clipboard.query` work uses the existing FIFO, at most one outstanding query and at most once per second while the controller is open. Existing polling loops and intervals are untouched. Server epoch, semantic revision, snapshot age, active UUID, context/Develop counters and timestamp bind admission. Lua retains catalog object/path, active local identifier/UUID and exact full selected-photo membership; same-count changes with the same active photo are rejected. A missing active photo is rejected before `getTargetPhotos()` can use its all-Filmstrip fallback.

Requests consume an ID for the entire server epoch, with a bounded store refusing new IDs at capacity instead of evicting old ones. One-use claims and Lua high-water marks prevent duplicate/reloaded dispatch; direct command and batch injection cannot bypass ownership. Copy/Paste queue boundaries prevent later coalesced edits from replacing earlier edits across either action. Both use ordinary queue capacity.

Paste acquires a synchronous SDK write gate, revalidates server ownership/context **inside the gate**, then rechecks native catalog/photo/complete selection after the yielding HTTP/UUID reads. There is no network call or explicit yield between that final check and the single SDK call. Exceptions are caught inside the gate, preventing error reporting from requesting a rollback. Copy uses the same final guards without a write gate. Lifecycle shutdown/generation replacement rejects old work.

Before the claim, changed context invalidates the request. After the claim, the receipt remains bound to its captured targets: Paste's own Develop feedback or subsequent user navigation must not discard an otherwise valid result or retarget a write. The inside-gate validator still requires the original context before invocation. A claimed operation has a bounded 120-second result window; uncertainty retains a review interlock, rejects late settlement and never automatically retries. **I've checked Lightroom** only acknowledges uncertainty; it performs no Copy/Paste.

## HTTP contract

The existing local GET/proxy conventions apply; responses are not cached. Client paths use `/api/clipboard/` through the controller proxy.

- `/clipboard/state`: no query fields. Returns the selection/capability snapshot, epoch/revision, context, age, pending operation, last result and uncertainty flag. `available` refers to native selection feedback, never clipboard contents.
- `/clipboard/action`: exact fields `command=clipboard.copy|clipboard.paste`, `requestId`, `serverEpoch`, `stateRevision`, `selectionToken`, `activeModule`, `selectedPhotoUuid`, `contextCounter`, `developCounter`, `contextChangedAt`, from one fresh snapshot. AI behavior is fixed by the server, not a caller override. Missing/extra/duplicate fields or unsupported command names produce 400; unavailable/busy/stale or invalid bindings produce 409. Identical duplicate IDs return a receipt without re-enqueueing; changed inputs with a consumed ID are rejected.
- `/clipboard/acknowledge`: exact `serverEpoch` and uncertain `operationId`. Explicit user review only.
- `/clipboard/query-result`, `/clipboard/claim`, `/clipboard/validate`, `/clipboard/operation-result`: internal protocol endpoints bound to outstanding commands. Validate rechecks a consumed claim without granting a second dispatch. Native results include `outcome`, `invoked`, `sdkResult`, `aiPendingCount` and `aiCheckedCount`; the server receipt adds the captured `targetCount`. HTTP admission is not SDK success.
